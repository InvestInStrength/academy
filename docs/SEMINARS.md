# Seminars — the second certification kind

A **seminar** is a single event (e.g. an online seminar) that is certified with a
questionnaire in exactly the same way as a course. It is **not** a parallel
system: a seminar is a `courses` row with `kind = 'seminar'`.

```
courses (kind = 'course' | 'seminar')
  ├── course_topics
  ├── questions           (course_id, topic_id nullable)
  └── questionnaires      (course_id, passing %, template override)
        └── certification_assignments (participant + questionnaire + token)
              └── attempts → certificates → assets / email / public verify
```

Everything below `courses` is kind-agnostic and was not changed. That is the
whole point of the design: assignments, attempts, scoring, recommendations,
certificate issuing, PDF/PNG generation, email and public verification all work
for a seminar without knowing it is one.

## What actually differs

| | Course | Seminar |
|---|---|---|
| Admin section | `/admin/courses` | `/admin/seminars` |
| Event date | — | `courses.event_date`, printed on the certificate |
| Topics on the certificate | yes, chosen per assignment | **never** |
| Certificate template | built-in course template | own artwork per seminar |

Three rules worth knowing:

1. **`kind` is immutable after creation.** `updateCourse` reads the stored kind
   from the database rather than trusting the posted field, so a record can never
   move between the two admin sections (which would also silently change which
   template its future certificates use).
2. **A seminar's topics are never printed.** They are still useful — they group
   its questions and drive the per-topic learning recommendations a candidate
   sees after a failed attempt — so the topics section stays on the seminar page,
   but `issueCertificate` skips `certification_assignment_topics` entirely for a
   seminar, and the assignment UI hides the topic picker.
3. **The event date is a `date`, not a timestamp.** `render.ts` parses
   `YYYY-MM-DD` as local midnight; using `new Date()` directly would print the
   previous day in any negative-offset timezone.

## Certificate templates

Each seminar ships its own designed SVG — the seminar name, its series and its
number are part of the artwork, not data. Resolution at issue time, most
specific first:

```
questionnaires.certificate_template_id     (narrow override, unused by the UI)
  → courses.certificate_template_id        (the seminar's own artwork)
    → built-in template for courses.kind   (render.ts → defaultTemplateFor)
```

Templates are managed at **`/admin/settings/templates`** and assigned on the
course/seminar edit form.

### Template requirements

The renderer substitutes `{{placeholder}}` tokens and freezes the result into
`certificate_public_snapshot`, then rasterises it server-side with no network and
no working directory. Two consequences that are easy to get wrong:

- **Variable fields must be live text, not outlines.** If a designer exports with
  "convert text to outlines", the `{{...}}` tokens become vector glyphs and there
  is nothing to substitute — the certificate prints the literal `{{...}}` shapes.
  Barlow is bundled with the renderer (`src/lib/certificate/fonts/`), so live
  text renders identically. The upload form and
  `scripts/import-certificate-template.mjs` both detect and refuse this.
- **Linked images must be embedded** as `data:` URIs. A relative
  `xlink:href="photo.jpg"` silently disappears from the finished certificate.
  `scripts/import-certificate-template.mjs` inlines them automatically; the
  upload form rejects them (the browser cannot read the sibling file).

A template is also rejected if it has **no name placeholder**
(`{{participant_name}}` / `{{certificate_display_name}}` / `{{candidate_name}}`)
— a certificate that cannot name its holder is never what was intended, and its
absence is the same outlined-export signature.

Recognised tokens are listed in `src/lib/certificate/render.ts` and mirrored in
`admin/settings/templates/schema.ts` (`KNOWN_PLACEHOLDERS`).

### Why template SVGs are treated as untrusted

Before template CRUD existed, every certificate SVG was generated by us from
XML-escaped data, so inlining it into a page was safe. That is no longer true:
an admin can now upload arbitrary SVG, it is rendered into a certificate, frozen
into the immutable `certificate_public_snapshot`, and served from the **public**
verification page. Executable markup in a template would therefore run for every
visitor of a certificate's QR link, on the platform's own origin, from data that
cannot be edited afterwards.

Two independent layers, both required — do not remove one on the strength of the
other:

1. **Isolated render.** `CertificateView` renders the snapshot as
   `<img src="data:image/svg+xml;base64,…">`. Browsers never execute scripts,
   event handlers or external fetches in an SVG loaded through `<img>`. This
   holds even for snapshots frozen before layer 2 existed. The certificate is a
   static document, so nothing is lost by isolating it.
2. **Sanitise on write.** `sanitizeTemplateSvg` (`lib/certificate/template-import.ts`)
   strips `<script>`, `<foreignObject>`, every `on*` handler attribute and
   `javascript:` / `data:text/html` URLs before the template is stored — which
   also keeps hostile markup away from the server-side rasteriser. The Zod schema
   validates the **normalized** string, so what is validated is exactly what is
   stored, and requires it to *start with* `<svg` rather than merely contain it.

### The built-in seminar template

`src/lib/certificate/seminar-template.ts` **derives** the interim seminar
template from the course template at module load, rewriting only the
course-specific lines:

- `Advanced Pre-/ Rehabilitation` → `Seminar`
- `has successfully attended all **12 modules** and passed the certification test`
  (three positioned `<text>` elements) → one centered sentence about the seminar
- `Topics covered: {{included_topics}}` → `{{event_date}}`

Deriving rather than inlining a second 145 KB SVG means designer artwork updates
(`scripts/update-certificate-template.mjs`) land on both certificates. The
rewrites degrade gracefully if a marker disappears, so
`seminar-template.test.ts` is what catches drift — keep it.

## Scripts

```bash
# Import a designer SVG as a certificate template (inlines linked images,
# refuses an outlined-text export)
node scripts/import-certificate-template.mjs <file.svg> "<template name>"

# Seed the Applied Shoulder Biomechanics seminar + question bank + test
node scripts/seed-shoulder-biomechanics.mjs [--dry-run]
```

Both need `NEXT_PUBLIC_SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` in
`.env.local`, and both are idempotent (matched by name/title).

## Adding a seminar by hand

1. `/admin/seminars` → title + event date + certificate template.
2. Optional: topics on the seminar page (for learning recommendations only).
3. `/admin/questions` → questions, picking the seminar in the course dropdown
   (courses and seminars are shown as separate groups).
4. `/admin/questionnaires` → build the test, set the pass mark, activate.
5. `/admin/participants` → create the assignment; the invite email goes out
   automatically when the participant has an email address.
